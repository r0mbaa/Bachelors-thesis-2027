# core/topology — M1. Топология склада и адресное хранение

Склады, зоны, места хранения. Координаты, коды и вместимость ячеек стеллажей не вводятся руками: их выводит из планировки библиотека `layout`, а в таблицу переносит [`core.layout`](../layout).

**Требования:** FR-M1-01 .. FR-M1-14. **Модель данных:** §11.1. **Геометрия:** §8.1.

## Места хранения

| Вид | Код | Откуда берётся |
| --- | --- | --- |
| Ячейка стеллажа | `WH1-R03-12-4-2-K` | Материализация планировки |
| Зона приёмки | `WH1-RECEIVING` | Создаётся вместе со складом |
| Зона отгрузки | `WH1-SHIPPING` | Создаётся вместе со складом |
| Тара сборщика | — | Появится вместе со справочником тары |

Виртуальные места нужны, чтобы каждое изменение остатка было движением «откуда → куда» внутри одного журнала: приёмка кладёт товар в `RECEIVING`, размещение переносит его в ячейку, отбор — в тару.

Ячейка, исчезнувшая из планировки, не удаляется, а помечается неактивной: на неё ссылается история движений.

## Зоны

Зона задаёт тип своих ячеек и **политику хранения** (FR-M6-02a, INV-08): выделенное место (один SKU — одна ячейка отбора) или свободное размещение. Склад создаётся с зоной `MAIN` — отбор с выделенным местом, потому что в этом режиме идёт демонстрация (§11.2). Ряды переводятся в зону целиком (`PUT /warehouses/{wh}/zones/{zone}/rows`). Отдельной ячейке можно назначить свой тип, например брак (FR-M1-05).

## API

| Запрос | Роль |
| --- | --- |
| `GET /api/v1/warehouses`, `/warehouses/{wh}`, `/warehouses/{wh}/zones` | любая |
| `GET /api/v1/warehouses/{wh}/locations?row=&zone=&type=&blocked=` | любая, постранично |
| `GET /api/v1/locations/{code}` | любая |
| `POST /api/v1/warehouses`, `/warehouses/{wh}/zones`, `PUT …/zones/{zone}/rows`, `PUT /locations/{code}/type` | `WAREHOUSE_ADMIN` |
| `POST /api/v1/locations/{code}/block`, `/unblock` (FR-M1-11) | `WAREHOUSE_ADMIN`, `DISPATCHER` |

Все расстояния хранятся в метрах. Отдельная настройка единиц измерения из FR-M1-01 не заведена: пересчёт единиц — забота отображения, а не учёта.
