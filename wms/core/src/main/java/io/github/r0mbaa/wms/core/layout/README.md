# core/layout — M15. Конструктор склада, серверная часть

Хранение планировки с версиями, импорт и экспорт в JSON (FR-M15-10), перенос ячеек в учёт после сохранения версии.

Вся геометрия — генерация ячеек (FR-M15-05), построение графа (§8.7), валидация (FR-M15-07), классификатор топологии (FR-M15-08), параметрический мастер (FR-M15-09) — находится в библиотеке `layout`. Этот пакет её вызывает и ничего не вычисляет сам. Благодаря этому стенд `research` получает те же ячейки и тот же граф без БД.

Редактор и трёхмерная сцена — в модуле `web`. Принцип разделения: редактирование только в 2D, отображение в 3D (§7.15.1).

**Требования:** FR-M15-01 .. FR-M15-31.

## Версии

| Запрос | Что делает |
| --- | --- |
| `GET /api/v1/warehouses/{wh}/layout` | Текущий документ планировки (экспорт) |
| `PUT /api/v1/warehouses/{wh}/layout` | Новая версия (импорт), только `WAREHOUSE_ADMIN` |
| `GET …/layout/versions`, `…/versions/{n}` | История версий |
| `POST /api/v1/warehouses/{wh}/layout/check` | Проверка без сохранения: замечания валидации и что изменится в ячейках |
| `GET /api/v1/warehouses/{wh}/layout/graph` | Граф текущей версии: узлы, рёбра, ячейка → точка отбора |
| `POST /api/v1/warehouses/{wh}/layout/wizard` | Мастер типовой планировки (FR-M15-09): документ поверх текущей версии, готовый к `PUT` |
| `GET /api/v1/rack-profiles/standard` | Типовые профили стеллажей (FR-M15-03d) |

Документ — это JSON записи `Layout` из библиотеки `layout`. Формат экспорта и импорта один и тот же. Поле `version` в сохраняемом документе означает версию, от которой шло редактирование. Если с тех пор кто-то сохранил другую, запрос получает 409, и чужие изменения не перезаписываются молча. Сохранения одного склада сериализуются блокировкой строки склада.

Версии не удаляются, чтобы маршруты прошлых заданий оставались воспроизводимыми.

## Проверка перед сохранением

Планировку с ошибками валидации сохранить нельзя: ответ 422 содержит список `issues` с типом замечания, текстом, областью на плане и номерами рядов, по которым конструктор подсвечивает места (FR-M15-07). Предупреждения сохранению не мешают.

`POST …/layout/check` делает ту же проверку без сохранения и дополнительно показывает, что изменится в учёте (FR-M15-03c): сколько ячеек появится и исчезнет и в каких исчезающих ячейках лежит товар. Сохранение такой планировки всё равно отвергнет `InventoryGuards`, а предпросмотр показывает это заранее, пока пользователь редактирует план.

## Граф

Граф строится библиотекой `layout` по текущей версии и кэшируется по ключу «склад + версия». Версии неизменяемы, поэтому граф из кэша не устаревает: новая версия просто получает новый ключ (§8.7, Д4).

Мастер ничего не сохраняет. Он строит документ поверх текущей версии склада, а конструктор показывает его и сохраняет обычным `PUT`. Так результат мастера проходит ту же проверку и попадает в ту же историю версий, что и ручная расстановка.

## Материализация ячеек

После сохранения версии `CellMaterializer` переносит ячейки в таблицу `location` пакетным `INSERT … ON CONFLICT (code)` мимо JPA, иначе склад в 20 тыс. ячеек сохранялся бы секундами (NFR-P-08).

- Ячейка опознаётся по коду, а код строится от неизменного номера ряда (§8.7, В2). Поэтому перенос ряда обновляет координаты существующих ячеек, и остатки с историей остаются на месте.
- Зона, тип и блокировка существующей ячейки не трогаются: их задают вне конструктора.
- Новая ячейка попадает в зону, где уже лежит большинство ячеек её ряда. Ячейки нового ряда попадают в зону `MAIN`.
- Ячейки, которых нет в новой версии, помечаются неактивными.
