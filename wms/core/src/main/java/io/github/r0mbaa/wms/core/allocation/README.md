# core/allocation — M6. Аллокация и резервирование (состояние)

Транзакционная часть M6: какие ячейки и сколько закреплены за строкой заказа, и резерв в таблице остатков.

Алгоритмическая часть — стратегии выбора ячеек (ближайшая к депо, минимальный остаток, совместная с маршрутизацией, FR-M6-06) — будет в модуле `planner-engine`, пакет `engine.allocation`. Разрез намеренный: состояние резервов принадлежит `core`, правило выбора — планировщику (§12.2). В `core` есть только интерфейс `AllocationRule` и резервное правило «минимум затрагиваемых ячеек», которое работает без планировщика (NFR-R-05). Ответ правила проверяется, а не принимается на веру: правило подключаемое.

**Требования:** FR-M6-01 .. FR-M6-06. **Постановка:** §8.4. **Инвариант:** INV-03.

## Конкурентность

Два механизма, как в §12.2:

| Что резервируется | Механизм | Почему |
| --- | --- | --- |
| Один заказ, в том числе срочный | Оптимистическая блокировка `@Version` на строках остатка. При конфликте вся аллокация повторяется в новой транзакции, до `wms.allocation.max-attempts` раз | Конфликты редки, а блокировка строк на время расчёта задерживала бы терминалы. Конфликт вызывает повтор, а не ошибку у пользователя (NFR-R-02) |
| Волна | `PESSIMISTIC_WRITE` на всех строках-кандидатах сразу, в порядке id места и SKU | Волна трогает много строк, и повтор целиком дорог. Единый порядок захвата исключает взаимную блокировку параллельных волн |

`hibernate.order_updates` включён, поэтому конкурентные оптимистические аллокации обновляют строки остатка в одном порядке и тоже не блокируют друг друга взаимно.

Остаток в волне распределяется в её порядке: заказ с ближайшим дедлайном и большим приоритетом получает товар первым.

## Жизненный цикл резерва

`RESERVED → PICKED | FAILED` по итогам отбора или `RESERVED → RELEASED`, когда резерв снят:

- **отмена заказа** — слушатель `OrderCancelled` снимает резервы в транзакции отмены (FR-M5-07);
- **вручную** — `POST /api/v1/orders/{number}/release`, заказ возвращается в `NEW`;
- **по сроку** (FR-M6-04) — резерв заказа, ещё не вошедшего в задание, живёт `wms.allocation.reservation-ttl` (по умолчанию 4 ч), после чего фоновая задача его снимает. Когда заказ входит в задание, срок снимается.

Недостача не мешает резервированию: что не хватило, видно в ответе как `shortage` (FR-M5-04), а повторный вызов дорезервирует, когда товар поступит.
