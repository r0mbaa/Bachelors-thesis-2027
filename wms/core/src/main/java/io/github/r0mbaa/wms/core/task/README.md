# core/task — M9, M10. Задания, тара, сборщики, терминал

Тара и тележки, реестр сборщиков, батчи и задания на сборку, их назначение и жизненный цикл.

Батчинг, маршрутизация и правило назначения — предмет исследования и живут в модуле `planner-engine` (пакеты `engine.batching`, `engine.routing`, `engine.dispatch`). Здесь хранится состояние и есть **ручной режим**, который работает и без планировщика (NFR-R-05).

**Требования:** FR-M9-01 .. FR-M9-09, FR-M10-01 .. FR-M10-12 (серверная часть), FR-M13-04, FR-M7-02, FR-M7-03. **Инварианты:** INV-05, INV-09.

## Модель

| Сущность | Что это |
| --- | --- |
| `Container` | Тара или тележка (FR-M13-04): вместимость по объёму и весу, число отделений. У каждой тары своё виртуальное место `WH1-CNT-<код>`, где отобранное лежит до отгрузки (FR-M10-11, INV-09) |
| `Worker` | Сборщик (FR-M9-01): учётная запись с ролью `PICKER`, код бейджа (`WRK:…`), PIN для терминала (хэш), статус, последняя подтверждённая ячейка |
| `Batch` | Заказы, собираемые за один проход, с отделением тележки под каждый заказ. Хранит, каким алгоритмом батчинга и маршрутизации построен, чтобы результаты были воспроизводимы |
| `Task` | Батч, назначенный сборщику, с маршрутом из шагов |
| `TaskStep` | Ячейка, товар, количество, отделение тележки и резерв, из которого берётся товар |

## Ручное формирование задания

`POST /api/v1/tasks {warehouse, orders, container}`:

- в задание входят только зарезервированные заказы, каждый целиком (FR-M7-03), каждый в своё отделение;
- число заказов не больше числа отделений, а вес и объём не больше вместимости тары (FR-M7-02);
- тара активна, не занята другим активным заданием и пуста: прошлую сборку сначала раскладывают по заказам;
- шаги строятся из активных резервов и идут в **порядке адресов ячеек**. Адрес строится от начала координат склада, поэтому это обход ряд за рядом, а не оптимальный маршрут. Алгоритм записывается как `address_order`, батчинг — как `manual`;
- заказы переходят в `PLANNED`, их резервы перестают истекать.

Номер шага уникален в задании (INV-05, ограничение БД), а непрерывность ряда обеспечивает построение задания.

## Диспетчер

| Запрос | FR |
| --- | --- |
| `GET /api/v1/tasks?warehouse=&status=` — монитор, по умолчанию активные задания | FR-M9-07 |
| `POST …/{number}/assign {worker}` — назначить или передать начатое задание с прогрессом | FR-M9-05 |
| `POST …/{number}/unassign` — вернуть в очередь с сохранением пройденных шагов | FR-M9-06 |
| `PUT …/{number}/priority` | FR-M9-05 |
| `POST …/{number}/cancel` — расформировать не начатое задание: заказы возвращаются в `ALLOCATED`, срок резервов отсчитывается заново, тара освобождается | — |

Отмена заказа до начала сборки убирает его шаги из не начатых заданий (слушатель `OrderCancelled`). Задание, в котором не осталось шагов, отменяется.

Тара: `/api/v1/containers` (`WAREHOUSE_ADMIN`). Сборщики: `/api/v1/workers` (`WAREHOUSE_ADMIN`, `SYSTEM_ADMIN`; просмотр — ещё и `DISPATCHER`).

## Терминал сборщика (M10, процесс §6.3)

Вход — `POST /api/v1/auth/badge {badge, pin}`: скан бейджа `WRK:…` и PIN (FR-M10-02). Выдаются те же токены, что при обычном входе. Остальное — `/api/v1/terminal`, роль `PICKER`. Каждый ответ содержит текущее состояние задания: прогресс N из M (FR-M10-05) и текущий шаг крупно — адрес, ряд, секцию, ярус, высоту полки, товар, количество, отделение тележки (FR-M10-03).

| Запрос | Что делает |
| --- | --- |
| `POST /shift/start`, `/shift/break`, `/shift/end` | Смена. Уход со смены возвращает задание в очередь с сохранением пройденных шагов (FR-M9-06) |
| `POST /task/next` | Выдаёт назначенное задание или первое в очереди по раннему дедлайну, затем по приоритету. Очередь читается с `SKIP LOCKED`, поэтому два сборщика одновременно получают разные задания. Это простое правило, а не исследуемая диспетчеризация (§15.4) |
| `POST /task/start {container}` | Скан тележки: сборщик подтверждает, что взял ту, что в задании (§6.3, шаг 1). Заказы переходят в `IN_PROGRESS` |
| `POST /steps/{id}/confirm` | Скан товара и количество (по умолчанию требуемое, FR-M10-04c) |
| `POST /steps/{id}/exception` | Исключение §6.4 (FR-M10-06) |
| `POST /task/complete` | После последней точки: заказы получают `PICKED` или `PARTIALLY_PICKED` |

**Подтверждение шага** требует скана только товара (FR-M10-04). Отсканирован не тот товар — отказ с указанием, какой нужен. Скан полки запрашивается, только если товар лежит в нескольких ячейках зоны: иначе по скану товара не понять, откуда он взят (FR-M10-04a, INV-08). В зоне с выделенным местом так не бывает. Маршрут проходится строго по порядку.

Подтверждение переносит товар из ячейки в тару движением `PICK` и закрывает резерв строки (FR-M10-11). Со склада товар списывается только при отгрузке, поэтому остаток мест тары — это отобранное, но не отгруженное (INV-09).

**Идемпотентность** (FR-M10-08, NFR-R-03): терминал генерирует ключ на каждое действие. Ключ вставляется в `terminal_event` с `ON CONFLICT DO NOTHING` в той же транзакции, что и отбор. Повторная отправка после обрыва связи возвращает текущее состояние и не создаёт второго движения. События одного задания обрабатываются по очереди под блокировкой строки задания. Блокировка берётся до загрузки задания, чтобы работать со свежим состоянием.

**Ручной ввод кода** вместо сканирования (FR-M10-04b, NFR-SEC-06) разрешён только ролям из `wms.terminal.manual-entry-roles` (по умолчанию `DISPATCHER`, `WAREHOUSE_ADMIN`) и пишется в аудит.

**Исключения §6.4:**

| Тип | Что происходит |
| --- | --- |
| `INSUFFICIENT` | Отбирается фактическое, строка закрывается частично |
| `MISSING` | Ничего не отобрано, резерв снят |
| `DAMAGED` | Годное отбирается, повреждённое списывается из ячейки движением `WRITE_OFF` |
| `LOCATION_UNAVAILABLE` | Точка пропускается |
| `MISPLACED` | Точка пропускается, ячейка блокируется до инвентаризации |

Неотобранное по резерву остаётся в ячейке свободным. Переаллокацию остатка строки в другую ячейку и перестроение остатка маршрута (§6.4, FR-M8-07) выполнит планировщик; пока недобранное видно в заказе и решается диспетчером.

Offline-режим (FR-M10-07) урезан (§3.2). Возврат собранного при отмене после сборки (FR-M10-12) пока не реализован.

## Не реализовано

Зоны и квалификация сборщиков (FR-M9-04), балансировка загрузки (FR-M9-08) и заторы в проходах (FR-M9-09) пока не реализованы.
